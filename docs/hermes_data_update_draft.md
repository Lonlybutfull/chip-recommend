# 基于 Hermes 的芯片模型知识图谱持续更新方案（思路草稿）

> 文档状态：讨论稿  
> 核心目标：在现有数据和爬取资产基础上，建设一套由 Hermes 周期调度、多个 Agent 协同、可增量运行且全程可追溯的数据更新系统。

## 一、背景与目标

目前算力推荐模块的主体功能已经基本完成，下一阶段的重点应从“推荐逻辑建设”转向“底层数据长期运营”。推荐结果是否可信，最终取决于芯片规格、模型信息、芯片×模型实测、兼容关系和部署文档是否真实、完整并且持续更新。

项目之前已经基于本地 DeepSeek 和一批 Python 脚本完成过集中式数据抓取与扩充。下一步不宜简单重复一次全量爬取，而应基于 Hermes 的心跳、Agent 和 Skill 机制，把这些历史资产改造成一套可以例行运行的数据更新闭环。

这套系统希望解决四个问题：

1. 定期复查历史来源，及时发现官网、文档和测试结果的变化。
2. 从网络中发现新的芯片、模型、实测、兼容性和部署资料。
3. 持续为非官方数据寻找更权威的官方依据，提高数据可信度。
4. 对新旧数据进行去重、冲突判断、融合和溯源，避免重复抓取与错误覆盖。

## 二、现有资产基础

项目并不是从零开始，已经形成了较完整的数据底座和一批可复用的采集资产。

### 1. 数据资产

当前数据库主要包含：

| 数据类型 | 当前规模 |
|---|---:|
| 芯片 | 1,093 |
| 模型 | 1,370 |
| 芯片×模型实测 | 3,517 |
| 兼容性记录 | 1,541 |
| 字段级溯源记录 | 12,391 |
| 信息来源链接 | 487 |

此外还有 473 条历史来源 CSV、DBGPU 数据、芯片发现结果、HuggingFace 原始模型数据以及多份数据库备份。

### 2. 历史抓取与处理能力

现有代码已经覆盖以下环节：

- 芯片网页、模型 API、benchmark、价格四类抓取管道；
- 芯片候选发现、系列扩展和初步名称去重；
- 芯片硬件字段、实测和价格的解析；
- HuggingFace 模型信息与 config.json 获取；
- 芯片、模型、benchmark、兼容性的数据写入；
- 芯片重复记录合并和来源官方性分类；
- 基于 `field_provenance` 的字段级来源记录。

现有 `chip-catalog`、`chip-enrich`、`chip-recommend-cli` 和 `chip-selector-agent` 等 Skill 也可以继续利用，但需要更新路径、命令、数据规模、评分版本和无人值守运行规则。

## 三、目前存在的主要问题

现有能力更接近“一次性批处理脚本”，距离长期自动运行仍有一些差距：

1. 链接库只保存 URL 和简单分类，没有上次抓取时间、下次检查时间、内容哈希、ETag、失败次数等状态。
2. 很多任务每次都会重新抓取，无法可靠判断网页是否真正发生变化。
3. 模型管道偏向“只新增不更新”，没有充分利用 HuggingFace 的 `lastModified` 做增量同步。
4. 芯片名称去重已有基础，但 benchmark 等关系数据仍可能重复。
5. 抓取、提取和写库之间缺少统一的候选数据暂存层，Agent 的结果容易直接影响正式数据。
6. 来源只有“官方/非官方”布尔标志，无法充分区分厂家规格、官方项目文档、MLPerf、权威第三方和普通社区。
7. 多个 Agent 如果直接并行写 SQLite，容易出现锁竞争和冲突覆盖。
8. Hermes、Claude 和 Agent 目录中存在多份 Skill 副本，长期维护容易发生版本漂移。

因此，新方案的关键不是继续增加零散脚本，而是增加统一的调度、状态、候选、融合和发布机制。

## 四、总体架构思路

建议采用“心跳调度、多 Agent 并行采集、统一暂存、单点发布”的结构：

```text
Hermes Heartbeat
        │
        ▼
数据更新协调 Agent
        │
        ├── 历史来源复查
        ├── 新来源与新实体发现
        ├── 非官方数据来源升级
        ├── 模型增量同步
        └── 实测/兼容/部署信息更新
                    │
                    ▼
              候选数据暂存区
                    │
                    ▼
         实体匹配 → 校验 → 去重 → 冲突处理
                    │
                    ▼
             单一 Publisher 写库
                    │
                    ▼
       主数据 + 字段溯源 + 更新报告 + 审核队列
```

Hermes 心跳只负责定期检查任务、生成队列和控制每轮工作量，不直接执行长时间全量爬取。多个 Agent 可以并行搜索和解析，但不直接并发修改正式数据库，最终由 Publisher 串行提交。

## 五、核心任务划分

### 1. 历史来源复查

按照来源的重要程度和更新时间，周期性访问现有链接库。优先使用 ETag、Last-Modified 和正文内容哈希判断是否变化；网页未变化时只更新检查时间，不再调用模型解析。

### 2. 新来源与新实体发现

按厂商、产品系列和数据类型执行定向检索，发现新的芯片、模型、benchmark、兼容关系和部署文档。新链接先进入来源库，新实体先进入候选区，通过名称规范化和别名匹配后再决定新增或关联已有实体。

### 3. 非官方数据来源升级

定期筛选当前由社区、新闻或第三方支持的字段，并针对“实体名 + 字段名”搜索官方证据。

- 官方来源与现值一致：保留事实并补充更权威的溯源。
- 官方来源与现值冲突：只有在实体、字段和值都能由官方新增原文唯一确认，并通过影子库功能测试时才自动覆盖；否则拒绝本次更新。
- 未找到官方来源：保留当前值，但记录复查时间和当前可信等级。

不能通过直接修改旧记录的 `is_official` 来完成“官方化”，而应记录一条真正的新官方证据。

### 4. 结构化数据同步

HuggingFace API、MLPerf、GitHub Release 等结构化来源优先由确定性脚本同步。Agent 主要处理来源发现、语义判断和非结构化页面，不应替代稳定 API 能完成的工作。

## 六、Agent、Skill 与脚本的分工

### Agent：负责判断与协调

Agent 适合处理：

- 判断网页是否与目标芯片或模型相关；
- 从非结构化材料中识别字段和上下文；
- 判断名称是否可能指向同一个实体；
- 分析冲突来源并决定是否继续检索；
- 生成候选变更、逐字段原文证据和自动发布结果说明。

### Skill：负责业务规则

Skill 应描述：

- 每类数据要找什么；
- 字段定义、单位和格式；
- 来源优先级与可信度规则；
- 搜索策略和排除规则；
- 哪些情况可以自动通过；
- 哪些情况必须自动拒绝；
- 可调用哪些共享工具。

建议逐步形成以下 Skill：

- `data-update-orchestrator`
- `source-refresh`
- `source-discovery`
- `official-source-upgrade`
- `chip-catalog` / `chip-enrich`
- `model-sync`
- `benchmark-ingest`
- `compatibility-ingest`
- `deployment-guide-ingest`
- `data-quality-review`
- `data-publish`

### 脚本和 Tool：负责确定性操作

应建设一组可被多个 Skill 共用的工具：

- URL 获取、缓存、重试、限速和代理；
- HTML、PDF、JSON 文本提取；
- ETag、Last-Modified 和内容哈希；
- 名称规范化和实体别名匹配；
- 单位转换和字段格式校验；
- 候选事实写入和差异比较；
- 去重、融合和 provenance 写入；
- 任务锁、检查点、失败重试和运行报告。

原则上，稳定且可重复的事情交给脚本，不确定且需要语义理解的事情交给 Agent，业务约束集中写进 Skill。

## 七、增量更新与数据融合流程

建议每条数据统一经过以下步骤：

1. 根据更新时间和优先级选择本轮任务。
2. 获取来源并判断内容是否变化。
3. 从变化内容中提取候选事实，同时记录来源页面、位置、时间和提取器版本。
4. 通过规范名称、别名和业务唯一键匹配已有实体。
5. 比较当前值和候选值，执行格式、范围和交叉字段校验。
6. 按来源等级、证据数量和时效性决定自动接受、保持原值或进入审核。
7. 由单一 Publisher 在事务中写入主表和 `field_provenance`。
8. 输出本轮新增、更新、未变化、冲突、失败和待审核报告。

建议的来源优先级为：

```text
厂家规格/官方 API
    > MLPerf 等正式测试
    > 厂商声明
    > 官方项目文档
    > 权威第三方
    > 社区实测
    > 新闻/博客
    > LLM 推断
```

同等级来源之间再比较发布时间和证据数量。低等级的新来源不应仅因为时间更新就覆盖高等级旧来源。

## 八、运行周期建议

| 周期 | 主要任务 |
|---|---|
| 每小时 | 心跳检查队列、失败重试、超时任务和过期锁 |
| 每天 | HuggingFace 模型变化、新产品动态、GitHub/部署文档变化 |
| 每周 | 历史链接复查、benchmark、兼容性、部署信息和价格 |
| 每月 | 全网新实体发现、非官方来源升级、低质量数据专项清理 |
| 每季度 | 全库深度复核、失效链接检查、重复数据与覆盖率报告 |

每轮应设置抓取数量、运行时间和模型调用预算，建议先限制为 3～5 个并行采集 Agent，并按域名限速。

## 九、分阶段落地建议

### 第一阶段：跑通最小闭环

先选择一批已有官方芯片链接，实现：

```text
心跳 → 到期链接 → 变化检测 → 字段提取
     → 候选暂存 → 校验 → 发布 → 溯源 → 报告
```

这一阶段重点建设链接状态、运行批次、内容快照、候选事实和审核队列，不急于覆盖全部数据类型。

### 第二阶段：模型增量同步

利用 HuggingFace `lastModified` 增量更新模型 API、config.json 和模型卡，只处理新增或发生变化的模型。

### 第三阶段：关系数据更新

为 benchmark、兼容性和部署信息定义稳定业务唯一键，补充 update/upsert 接口，然后接入 Hermes 调度。

### 第四阶段：全网发现与来源升级

最后开放新实体发现和非官方数据官方化。这两类任务语义判断最多，应在候选区、审核队列和质量报告成熟后上线。

## 十、近期建议优先完成的工作

1. 确定唯一的 Skill 源目录，其他环境通过同步脚本生成，避免三套 Skill 漂移。
2. 更新旧版 `chip-catalog` 和 `chip-enrich`，适配当前目录、CLI 和定时运行模式。
3. 扩展 `link_library`，增加检查时间、调度时间、HTTP 状态、内容哈希、失败次数等字段。
4. 新增 `update_runs`、`source_snapshots`、`extraction_candidates`、`review_queue`、`entity_aliases` 等控制表。
5. 抽离统一抓取器、实体规范化器、字段校验器和 Publisher。
6. 先以 10～20 个官方芯片页面做 dry-run，验证无重复、无误覆盖且每次变化均可追溯。

## 十一、预期结果

最终希望形成的不是一个“自动填数据库的 Agent”，而是一套可持续的数据生产机制：

- 已知来源会被定期复查；
- 新来源和新实体能够被持续发现；
- 非官方数据会逐步获得更权威的证据；
- 未变化内容不会重复解析；
- 冲突数据不会被静默覆盖；
- 每次更新都能够说明来源、原因、执行批次和旧值变化；
- 多个 Agent 可以并行工作，但正式数据库始终安全、可回滚、可审计。

这套机制跑通后，再将更新后的数据稳定提供给算力推荐模块，推荐结果的可信度和时效性才会真正形成长期优势。
