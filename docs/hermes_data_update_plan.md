# 基于 Hermes 的芯片模型知识图谱持续更新方案（思路草稿）

> 文档状态：讨论稿  
> 核心目标：在现有数据和爬取资产基础上，建设一套由 Hermes 周期调度、多个 Agent 协同、可增量运行且全程可追溯的数据更新系统。

## 一、背景与目标

目前算力推荐模块的主体功能已经基本完成，下一阶段的重点应从“推荐逻辑建设”转向“底层数据长期运营”。推荐结果是否可信，最终取决于芯片规格、模型信息、芯片×模型实测、兼容关系和部署文档是否真实、完整并且持续更新。

项目之前已经基于本地 DeepSeek 和一批 Python 脚本完成过集中式数据抓取与扩充。下一步不宜简单重复一次全量爬取，而应基于 Hermes 的心跳、Agent 和 Skill 机制，把这些历史资产改造成一套可以例行运行的数据更新闭环。

这套系统希望解决四个问题：

1. 定期复查历史来源，及时发现官网、文档和测试结果的变化。
2. 从网络中发现新的芯片、模型、实测、兼容性和部署资料。
3. 持续为非官方数据寻找更权威的官方依据，提高数据可信度。
4. 对新旧数据进行去重、冲突判断、融合和溯源，避免重复抓取与错误覆盖。

## 二、现有资产基础

项目并不是从零开始，已经形成了较完整的数据底座和一批可复用的采集资产。

### 1. 数据资产

当前数据库主要包含：

| 数据类型 | 当前规模 |
|---|---:|
| 芯片 | 1,093 |
| 模型 | 1,370 |
| 芯片×模型实测 | 3,517 |
| 兼容性记录 | 1,541 |
| 字段级溯源记录 | 12,391 |
| 信息来源链接 | 487 |

此外还有 473 条历史来源 CSV、DBGPU 数据、芯片发现结果、HuggingFace 原始模型数据以及多份数据库备份。

### 2. 历史抓取与处理能力

现有代码已经覆盖以下环节：

- 芯片网页、模型 API、benchmark、价格四类抓取管道；
- 芯片候选发现、系列扩展和初步名称去重；
- 芯片硬件字段、实测和价格的解析；
- HuggingFace 模型信息与 config.json 获取；
- 芯片、模型、benchmark、兼容性的数据写入；
- 芯片重复记录合并和来源官方性分类；
- 基于 `field_provenance` 的字段级来源记录。

现有 `chip-catalog`、`chip-enrich`、`chip-recommend-cli` 和 `chip-selector-agent` 等 Skill 也可以继续利用，但需要更新路径、命令、数据规模、评分版本和无人值守运行规则。

## 三、目前存在的主要问题

现有能力更接近“一次性批处理脚本”，距离长期自动运行仍有一些差距：

1. 链接库只保存 URL 和简单分类，没有上次抓取时间、下次检查时间、内容哈希、ETag、失败次数等状态。
2. 很多任务每次都会重新抓取，无法可靠判断网页是否真正发生变化。
3. 模型管道偏向“只新增不更新”，没有充分利用 HuggingFace 的 `lastModified` 做增量同步。
4. 芯片名称去重已有基础，但 benchmark 等关系数据仍可能重复。
5. 抓取、提取和写库之间缺少统一的候选数据暂存层，Agent 的结果容易直接影响正式数据。
6. 来源只有“官方/非官方”布尔标志，无法充分区分厂家规格、官方项目文档、MLPerf、权威第三方和普通社区。
7. 多个 Agent 如果直接并行写 SQLite，容易出现锁竞争和冲突覆盖。
8. Hermes、Claude 和 Agent 目录中存在多份 Skill 副本，长期维护容易发生版本漂移。

因此，新方案的关键不是继续增加零散脚本，而是增加统一的调度、状态、候选、融合和发布机制。

## 四、总体架构思路

建议采用“心跳调度、多 Agent 并行采集、统一暂存、单点发布”的结构：

```text
Hermes Heartbeat
        │
        ▼
数据更新协调 Agent
        │
        ├── 历史来源复查
        ├── 新来源与新实体发现
        ├── 非官方数据来源升级
        ├── 模型增量同步
        └── 实测/兼容/部署信息更新
                    │
                    ▼
              候选数据暂存区
                    │
                    ▼
         实体匹配 → 校验 → 去重 → 冲突处理
                    │
                    ▼
             单一 Publisher 写库
                    │
                    ▼
       主数据 + 字段溯源 + 更新报告 + 审核队列
```

Hermes 心跳只负责定期检查任务、生成队列和控制每轮工作量，不直接执行长时间全量爬取。多个 Agent 可以并行搜索和解析，但不直接并发修改正式数据库，最终由 Publisher 串行提交。

## 五、核心任务划分

### 1. 历史来源复查

按照来源的重要程度和更新时间，周期性访问现有链接库。优先使用 ETag、Last-Modified 和正文内容哈希判断是否变化；网页未变化时只更新检查时间，不再调用模型解析。

### 2. 新来源与新实体发现

按厂商、产品系列和数据类型执行定向检索，发现新的芯片、模型、benchmark、兼容关系和部署文档。新链接先进入来源库，新实体先进入候选区，通过名称规范化和别名匹配后再决定新增或关联已有实体。

### 3. 非官方数据来源升级

定期筛选当前由社区、新闻或第三方支持的字段，并针对“实体名 + 字段名”搜索官方证据。

- 官方来源与现值一致：保留事实并补充更权威的溯源。
- 官方来源与现值冲突：进入审核队列，不自动覆盖。
- 未找到官方来源：保留当前值，但记录复查时间和当前可信等级。

不能通过直接修改旧记录的 `is_official` 来完成“官方化”，而应记录一条真正的新官方证据。

### 4. 结构化数据同步

HuggingFace API、MLPerf、GitHub Release 等结构化来源优先由确定性脚本同步。Agent 主要处理来源发现、语义判断和非结构化页面，不应替代稳定 API 能完成的工作。

## 六、Agent、Skill 与脚本的分工

### Agent：负责判断与协调

Agent 适合处理：

- 判断网页是否与目标芯片或模型相关；
- 从非结构化材料中识别字段和上下文；
- 判断名称是否可能指向同一个实体；
- 分析冲突来源并决定是否继续检索；
- 生成候选变更和人工审核说明。

### Skill：负责业务规则

Skill 应描述：

- 每类数据要找什么；
- 字段定义、单位和格式；
- 来源优先级与可信度规则；
- 搜索策略和排除规则；
- 哪些情况可以自动通过；
- 哪些情况必须人工审核；
- 可调用哪些共享工具。

建议逐步形成以下 Skill：

- `data-update-orchestrator`
- `source-refresh`
- `source-discovery`
- `official-source-upgrade`
- `chip-catalog` / `chip-enrich`
- `model-sync`
- `benchmark-ingest`
- `compatibility-ingest`
- `deployment-guide-ingest`
- `data-quality-review`
- `data-publish`

### 脚本和 Tool：负责确定性操作

应建设一组可被多个 Skill 共用的工具：

- URL 获取、缓存、重试、限速和代理；
- HTML、PDF、JSON 文本提取；
- ETag、Last-Modified 和内容哈希；
- 名称规范化和实体别名匹配；
- 单位转换和字段格式校验；
- 候选事实写入和差异比较；
- 去重、融合和 provenance 写入；
- 任务锁、检查点、失败重试和运行报告。

原则上，稳定且可重复的事情交给脚本，不确定且需要语义理解的事情交给 Agent，业务约束集中写进 Skill。

## 七、增量更新与数据融合流程

建议每条数据统一经过以下步骤：

1. 根据更新时间和优先级选择本轮任务。
2. 获取来源并判断内容是否变化。
3. 从变化内容中提取候选事实，同时记录来源页面、位置、时间和提取器版本。
4. 通过规范名称、别名和业务唯一键匹配已有实体。
5. 比较当前值和候选值，执行格式、范围和交叉字段校验。
6. 按来源等级、证据数量和时效性决定自动接受、保持原值或进入审核。
7. 由单一 Publisher 在事务中写入主表和 `field_provenance`。
8. 输出本轮新增、更新、未变化、冲突、失败和待审核报告。

建议的来源优先级为：

```text
厂家规格/官方 API
    > MLPerf 等正式测试
    > 厂商声明
    > 官方项目文档
    > 权威第三方
    > 社区实测
    > 新闻/博客
    > LLM 推断
```

同等级来源之间再比较发布时间和证据数量。低等级的新来源不应仅因为时间更新就覆盖高等级旧来源。

## 八、运行周期建议

| 周期 | 主要任务 |
|---|---|
| 每小时 | 心跳检查队列、失败重试、超时任务和过期锁 |
| 每天 | HuggingFace 模型变化、新产品动态、GitHub/部署文档变化 |
| 每周 | 历史链接复查、benchmark、兼容性、部署信息和价格 |
| 每月 | 全网新实体发现、非官方来源升级、低质量数据专项清理 |
| 每季度 | 全库深度复核、失效链接检查、重复数据与覆盖率报告 |

每轮应设置抓取数量、运行时间和模型调用预算，建议先限制为 3～5 个并行采集 Agent，并按域名限速。

## 九、分阶段落地建议

### 第一阶段：跑通最小闭环

先选择一批已有官方芯片链接，实现：

```text
心跳 → 到期链接 → 变化检测 → 字段提取
     → 候选暂存 → 校验 → 发布 → 溯源 → 报告
```

这一阶段重点建设链接状态、运行批次、内容快照、候选事实和审核队列，不急于覆盖全部数据类型。

### 第二阶段：模型增量同步

利用 HuggingFace `lastModified` 增量更新模型 API、config.json 和模型卡，只处理新增或发生变化的模型。

### 第三阶段：关系数据更新

为 benchmark、兼容性和部署信息定义稳定业务唯一键，补充 update/upsert 接口，然后接入 Hermes 调度。

### 第四阶段：全网发现与来源升级

最后开放新实体发现和非官方数据官方化。这两类任务语义判断最多，应在候选区、审核队列和质量报告成熟后上线。

## 十、近期建议优先完成的工作

1. 确定唯一的 Skill 源目录，其他环境通过同步脚本生成，避免三套 Skill 漂移。
2. 更新旧版 `chip-catalog` 和 `chip-enrich`，适配当前目录、CLI 和定时运行模式。
3. 扩展 `link_library`，增加检查时间、调度时间、HTTP 状态、内容哈希、失败次数等字段。
4. 新增 `update_runs`、`source_snapshots`、`extraction_candidates`、`review_queue`、`entity_aliases` 等控制表。
5. 抽离统一抓取器、实体规范化器、字段校验器和 Publisher。
6. 先以 10～20 个官方芯片页面做 dry-run，验证无重复、无误覆盖且每次变化均可追溯。

## 十一、预期结果

最终希望形成的不是一个“自动填数据库的 Agent”，而是一套可持续的数据生产机制：

- 已知来源会被定期复查；
- 新来源和新实体能够被持续发现；
- 非官方数据会逐步获得更权威的证据；
- 未变化内容不会重复解析；
- 冲突数据不会被静默覆盖；
- 每次更新都能够说明来源、原因、执行批次和旧值变化；
- 多个 Agent 可以并行工作，但正式数据库始终安全、可回滚、可审计。

这套机制跑通后，再将更新后的数据稳定提供给算力推荐模块，推荐结果的可信度和时效性才会真正形成长期优势。

## 十二、第一阶段实施规格（gstack 审查版）

第一阶段只验证“已知官方来源能否被安全、增量地复查”，范围固定为 10～20 条人工确认过的芯片官方链接。它会写入运行状态、来源快照和报告，但**不会自动修改** `chips`、`models`、`chip_model_benchmarks`、`chip_model_compatibility` 或 `field_provenance`。

### 1. 本阶段目标

- 同一来源没有变化时，不重复下载正文和触发后续解析。
- 来源发生变化时，保存可复核的快照，并进入“待提取”状态。
- 超时、限流、证书、页面过大、数据库锁等失败都有明确记录和重试时间。
- 每次运行输出结构化摘要，Hermes 可以根据退出码和 JSON 结果决定是否重试或通知。
- 所有测试使用临时数据库和本地 HTTP 夹具，不访问也不修改正式数据。

### 2. 明确不做的内容

- 不自动提取或发布芯片字段；等变化检测稳定后再接入 `chip-enrich`。
- 不做模型、benchmark、兼容性和部署信息同步；这些属于后续阶段。
- 不做全网新实体发现和非官方来源升级。
- 不在第一阶段引入消息队列、分布式数据库或多写入者架构。
- 不改算力推荐页面和评分逻辑。

### 3. 实施架构

```text
Hermes / 人工命令
        │ 显式 link_ids、运行预算、dry-run
        ▼
source_refresh CLI
        │
        ├── 读取 link_library（只读）
        ├── 读取 source_monitor_state
        ├── HTTP 条件请求（ETag / Last-Modified）
        ├── 正文规范化 + SHA-256
        └── 单写入事务
              ├── update_runs
              ├── source_monitor_state
              └── source_snapshots（仅首次、变化或失败）
        │
        ▼
JSON 摘要 + 人类可读报告
```

不在原有 `crawl.py` 上继续叠加逻辑。旧管道保留，新建独立的 `chip_model/pipeline/source_refresh.py` 和入口 `scripts/run_source_refresh.py`，待新链路稳定后再逐步迁移旧能力。

### 4. 控制表

第一阶段只新增三张控制表，避免过早设计通用候选事实模型：

| 表 | 用途 | 关键字段 |
|---|---|---|
| `update_runs` | 一次运行的审计记录 | mode、status、started_at、finished_at、counts_json、error_summary |
| `source_monitor_state` | 每个链接的最新检查状态 | link_id、etag、last_modified、raw_hash、content_hash、last_checked_at、next_check_at、failure_count、last_error |
| `source_checks` | 每个 URL 每次检查的证据与恢复点 | run_id、link_id、http_status、change_status、old/new hash、content_path、fetched_at |

`source_monitor_state.link_id` 唯一，`source_checks` 对 `(run_id, link_id)` 建唯一约束，并对 `(link_id, fetched_at)` 建索引；控制表不写 `field_provenance`，因为它们记录的是运行元数据而非业务事实。

正文文件只写入配置的快照根目录，按 SHA-256 内容寻址，文件名不使用 URL 路径，避免路径穿越。先写临时文件再原子改名，成功后才提交数据库记录。默认只为 `new`、`changed` 保存正文；`unchanged` 只更新状态。

### 5. 状态与判定

```text
due ──请求成功 200──▶ new / changed / unchanged
 │                         │
 ├──服务器返回 304────────▶ unchanged
 │
 ├──超时/连接失败/429/5xx──▶ retry_wait
 │
 └──无效 URL/永久性 4xx────▶ failed

new / changed ──后续阶段提取成功──▶ extracted
              └─第一阶段结束时────▶ pending_extraction
```

判定顺序：

1. 有 ETag 时发送 `If-None-Match`；否则有 Last-Modified 时发送 `If-Modified-Since`。
2. `304` 直接记为 `unchanged`。
3. `200` 同时计算完整响应原始哈希与确定性规范化正文哈希；正文哈希与上次相同则为 `unchanged`，不同则为 `changed`，首次则为 `new`。截断文本只能用于报告预览，不能用于变化判定。
4. `429`、`5xx`、连接和读取超时按指数退避；普通 `4xx` 默认不自动重试。
5. `next_check_at` 由结果和失败次数计算，命令行可以覆盖，但必须有最大退避上限。

### 6. CLI 契约

链接库当前没有可靠的官方等级字段，因此首批运行不做“自动识别官网”，而是要求显式传入人工确认的链接 ID：

```bash
# 只预览将检查哪些来源，不发请求、不写状态
python scripts/run_source_refresh.py --link-ids 20,21,22 --dry-run

# 执行检查，只写控制表和快照，不改业务表
python scripts/run_source_refresh.py --link-ids 20,21,22 --apply-state
```

默认行为是 `--dry-run`。`--apply-state` 才允许写控制表；两种模式都不能写业务表。可选参数包括 `--limit`、`--timeout`、`--proxy`、`--snapshot-dir`、`--json-output` 和 `--verbose`。

正常结束退出码为 `0`；部分来源失败但本轮已完成为 `2`；配置或数据库错误导致整轮不能执行为 `1`。JSON 摘要至少包含：run_id、selected、new、changed、unchanged、retry_wait、failed、duration_ms 和每条来源的结果。

### 7. 错误与恢复

| 失败 | 处理 | 操作者看到 |
|---|---|---|
| URL 无效或协议不允许 | 在请求前拒绝 | 链接 ID、错误码、修复建议 |
| 连接/读取超时 | 记录失败并退避 | 超时阶段、当前重试次数、下次时间 |
| 429 | 尊重 `Retry-After`，否则指数退避 | 域名、HTTP 状态、下次时间 |
| 5xx | 有上限地重试 | 尝试次数和最后状态 |
| 证书或 DNS 错误 | 不吞异常，分类记录 | 原因和代理/网络检查建议 |
| 响应过大 | 流式读取并在上限处停止 | 实际/允许大小和配置项 |
| 正文提取为空 | 保存响应元数据，不覆盖旧哈希 | `empty_content`，等待人工检查 |
| SQLite busy/locked | 短暂退避后整批事务失败 | 未提交说明和重试命令 |
| 快照写入失败 | 不提交对应状态更新 | 文件路径、磁盘错误、无部分成功假象 |
| 进程中途退出 | 已完成 URL 保留，运行标记为可恢复 | 下次从未完成 URL 继续 |

HTTP 层只捕获 Requests 的具体异常；最外层可以捕获未知异常用于生成失败报告，但必须保留异常类型和上下文，不能静默继续。

### 8. 安全边界

- 只允许 `http` 和 `https`，拒绝 `file:`、本地文件路径和其他协议。
- 第一阶段的 URL 必须来自 `link_library` 的显式 ID，Hermes 不直接传任意 URL。
- 代理、超时、最大响应体和允许重定向次数均可配置并有安全默认值。
- 快照文件名不包含用户输入；日志不打印认证头、Cookie 或代理凭据。
- 正式库只有单一写入阶段；Agent 并行只产生结果，不并发写 SQLite。
- 第一阶段只运行一个抓取进程，并使用单实例锁；SQLite 设置有限 `busy_timeout`，数据库事务绝不跨越网络请求。

### 9. 测试与验收

新增 `tests/test_source_refresh.py`，使用临时 SQLite 和可注入的 HTTP Session/本地响应夹具。必须覆盖：

1. 首次 `200` 产生 `new`、哈希和快照。
2. 相同正文再次 `200` 产生 `unchanged`，不重复保存正文。
3. ETag 或 Last-Modified 被正确带入下一次请求，`304` 产生 `unchanged`。
4. 正文改变产生 `changed` 和新快照。

6. 失败次数、退避上限和 `Retry-After` 正确。
7. dry-run 不发请求、不写数据库和快照。
8. 快照写入失败时事务不产生“已成功”状态。
9. 重复执行 schema 初始化不会丢数据。
10. 并发写锁时给出可恢复错误，不产生半批状态。
11. 进程中途退出后重跑，已完成 URL 不重复处理，未完成 URL 能继续。

### 10. 部署、回滚与运行报告

部署顺序为：备份数据库 → 初始化控制表 → dry-run → 2 条来源 apply-state → 10～20 条来源试运行 → 检查报告 → 再接入 Hermes。新控制表和入口脚本不改变现有 API，因此旧服务可继续运行。

回滚时先停用 Hermes 任务，再回退代码。控制表属于附加数据，可保留用于审计；如需清理，应在备份后使用单独迁移，不在应用启动时自动删除。由于本阶段从未修改业务表，不需要回滚芯片数据。

每个 URL 在请求结束后用独立短事务写入 `source_checks` 并更新最新状态；失败不能覆盖上一次成功的 ETag、哈希和快照。每轮报告至少回答：检查了什么、哪些变化、哪些没变、哪些失败、为什么失败、下次何时重试、是否触碰业务表。Hermes 只有在 `changed`、连续失败达到阈值或整轮失败时才通知，平稳运行保持安静。
